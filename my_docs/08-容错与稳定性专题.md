## 0. 总览：故障模型与恢复责任

### 0.1 故障类型与处理方

| 故障 | 谁检测 | 谁恢复 | 默认行为 | 用户可调 |
|---|---|---|---|---|
| 用户代码抛异常 | 执行 worker | Owner 的 TaskManager | **不重试**，抛出 `RayTaskError` | `retry_exceptions=True/[Exc]` |
| Worker 进程崩溃 | raylet（socket 断开） | Owner 的 TaskManager（task）/ GCS（actor） | task 重试 3 次；actor 不重启 | `max_retries`、`max_restarts`、`max_task_retries` |
| OOM 被杀 | raylet MemoryMonitor | Owner 的 TaskManager | 可重试的 task **无限重试**（指数退避） | `task_oom_retries`、`memory_usage_threshold` |
| 对象丢失（节点挂掉） | Owner（节点死亡订阅） | ObjectRecoveryManager | 先找副本，再用 lineage 重建 | `max_retries`、`lineage_pinning_enabled`、`max_lineage_bytes` |
| Owner 死亡 | Borrower / raylet / GCS | 不可恢复 | `OwnerDiedError`；非 detached actor 随 owner 销毁 | `lifetime="detached"` |
| 节点故障 | GCS HealthCheck（约 15s） | 各 GCS Manager | task/actor 按上面规则恢复，PG 进入 RESCHEDULING | `health_check_*` |
| 节点抢占（drain） | Autoscaler / SIGTERM | 同上 | **不消耗**重试和重启次数 | `ray drain-node` |
| GCS 故障 | 各 GcsClient | GCS 重启后从存储恢复 | 存储在内存中：60s 后全集群退出 | Redis/RocksDB、`gcs_rpc_server_reconnect_timeout_s` |
| Head 节点故障 | — | 依赖 GCS FT 与外部编排（如 KubeRay） | 整个集群失效 | GCS FT |
| 网络抖动 | RetryableGrpcClient | 自动排队重发 | 透明重试，超时则失败 | `*_rpc_server_reconnect_timeout_*` |
| 对象存储满或磁盘满 | plasma CreateRequestQueue | spill、fallback 到文件系统分配 | 背压，最终报 `OutOfDisk` | `object_spilling_*`、`local_fs_capacity_threshold` |

### 0.2 分层恢复架构

```
┌──────────────────────────── 应用 / AI 库层 ─────────────────────────────┐
│ Serve: controller(detached, max_restarts=-1) + KV checkpoint + replica 健康检查 │
│ Train: FailureConfig + checkpoint + worker group 重启 + 弹性扩缩               │
│ Tune: trial 重试 + Tuner.restore │ Data: block 容错 + IO 重试 │ RLlib: EnvRunner 重启 │
├──────────────────────────── Ray Core 层 ───────────────────────────────┐
│ Owner(CoreWorker): TaskManager 重试 / ObjectRecoveryManager 重建 / ReferenceCounter │
│ GCS: GcsActorManager 重启 / PG 重调度 / HealthCheck / WorkerManager / JobManager      │
│ Raylet: Worker 死亡检测 / OOM Killer / Spill / Drain / 本地清理                       │
│ RPC: RetryableGrpcClient 透明重连                                                    │
├──────────────────────────── 集群层 ─────────────────────────────────┐
│ Autoscaler v1/v2: 替换故障/卡住的实例 │ KubeRay: head 重建 + GCS FT(Redis)        │
└──────────────────────────────────────────────────────────────────────┘
```

### 0.3 关键设计原则

1. **Ownership**：每个对象由创建它的 worker（owner）负责引用计数、位置记录和重建。owner 死亡后，它拥有的对象无法恢复，这是"共命运"（fate-sharing）的设计取舍。
2. **Actor 的重启集中在 GCS**：actor 创建任务固定 `max_retries=0`（`core_worker.cc` L2481）。重启完全由 `GcsActorManager::RestartActor` 决定。
3. **抢占不计次**：autoscaler drain 或抢占导致的失败，不消耗 task 的 `max_retries`，也不消耗 actor 的 `max_restarts`。
4. **Ray 不自动恢复应用状态**：actor 重启时会重新执行 `__init__`，状态需要用户自己做 checkpoint（`actors.md` L48）。

## 1. 故障检测

```
                     ┌─────────── GCS ───────────┐
   gRPC health check │ GcsHealthCheckManager      │◀── RaySyncer 心跳信号 (MarkNodeHealthy)
   ┌─────────────────│ period 3s, timeout 10s,    │
   │                 │ threshold 5, delay 5s      │
   ▼                 └──────┬─────────────────────┘
 raylet                      │ FailNode → GcsNodeManager::OnNodeFailure
   │ socket 断开              ▼ 发布 NodeRemoved → Resource/PG/Actor/Job/Autoscaler Manager
   │ (HandleClientConnectionError)
   ▼
 DisconnectClient → ReportWorkerFailure → GcsWorkerManager → OnWorkerDead(Actor/Task Manager)
                                                    └─ PublishWorkerFailure → 其他 raylet/owner
 CoreWorker ── 每 1s 检查 raylet PID；IPC 失败且 raylet 已死时 QuickExit
 CoreWorker ── GcsClient 60s 内连不上 GCS 就 _Exit
 Owner ←─ 节点存活订阅 → ResetObjectsOnRemovedNode → 对象恢复
 GCS ←─ 长轮询 owner(WaitForActorRefDeleted) → owner 死亡则销毁 actor
```

| 检测项 | 机制 | 位置 | 时效（默认） |
|---|---|---|---|
| 节点存活 | GCS 用 gRPC health check 探测 raylet；收到 RaySyncer 信号时跳过本轮探测 | `gcs/gcs_health_check_manager.cc` L143-219；配置在 `ray_config_def.h` L1123-1129 | 首次延迟 5s，周期 3s，超时 10s，连续失败 5 次判死，约 15-50s |
| 节点被误判死亡 | raylet 发现自己被标记为 DEAD 时直接 FATAL 退出 | `raylet/node_manager.cc` L955-975 | 立即 |
| Worker 进程 | raylet 检测到 Unix socket 断开 | `node_manager.cc` L1127-1158、L1464-1519 | 立即 |
| Worker 死因 | raylet 记录 `worker_failure_reasons_`，owner 通过 `GetWorkerFailureCause` 查询 | `node_manager.cc` L768-788；`normal_task_submitter.cc` L618-668 | — |
| Raylet 死亡（worker 视角） | 检查 raylet PID；IPC 失败时也会检查 | `core_worker.cc` L1069-1082（`raylet_death_check_interval_milliseconds=1000`）；`raylet_ipc_client.cc` L54-74 | 1s |
| GCS 不可达 | RetryableGrpcClient 超时后执行 `std::_Exit` | `gcs_rpc_client/rpc_client.h` L190-216 | 60s |
| Owner 死亡（对象） | Borrower 调用 `GetObjectStatus` 失败；raylet 订阅对象位置失败 | `future_resolver.cc` L52-66；`ownership_object_directory.cc` L354-365 | — |
| Owner 死亡（actor） | GCS 调用 `PollOwnerForActorRefDeleted`（长轮询） | `gcs_actor_manager.cc` L955-999 | — |
| Worker client 不可用 | 先向 GCS 查询节点状态，再调用 raylet 的 `IsLocalWorkerDead` 确认 | `core_worker_client_pool.cc` L28-88 | — |

## 2. Task 容错

### 2.1 选项

定义在 `python/ray/_common/ray_option_utils.py`（注意是 `_common`）：

| 选项 | 默认值 | 位置 | 语义 |
|---|---|---|---|
| `max_retries` | **3** | L182-184；`ray_constants.py` L648 `DEFAULT_TASK_MAX_RETRIES=3` | 系统故障（worker 或节点死亡）的重试次数，`-1` 表示无限 |
| `retry_exceptions` | False | L207-219 | `True` 表示所有应用异常都重试；传入异常类列表时只重试列表中的类型 |
| 环境变量 `RAY_TASK_MAX_RETRIES` | — | `remote_function.py` L426-433 | 覆盖全局默认值 |

```python
@ray.remote(max_retries=5, retry_exceptions=[ConnectionError, TimeoutError])
def fetch(url): ...
```

- **共用计数**：应用异常和系统故障共用同一个 `num_retries_left`（`normal_task_submitter.cc` L605-612）。
- **OOM 单独计数**：OOM 使用 `num_oom_retries_left`，不消耗 `max_retries`。但 `max_retries=0` 时 OOM 也不会重试（`task_manager.cc` L354-355）。
- **allowlist 判定**：在执行端判断，见 `_raylet.pyx` L880-929 的 `determine_if_retryable`。`UserCodeException` 会先解包到 `__cause__` 再做 isinstance 判断。

### 2.2 重试决策流程

```
执行失败
 ├─ 应用异常: reply.is_retryable_error 为真 → RetryTaskIfPossible(TASK_EXECUTION_EXCEPTION)
 └─ RPC 失败 (worker/节点死亡)
       └─ 向 raylet 查询 GetWorkerFailureCause(lease_id)   (normal_task_submitter.cc L560-587)
            ├─ raylet 返回原因 (如 OOM、fail_task_immediately)
            ├─ raylet 也不可达 → NODE_DIED
            └─ 默认 → WORKER_DIED
       → FailOrRetryPendingTask(fail_immediately)   (task_manager.cc L1676-1705)

RetryTaskIfPossible (task_manager.cc L1463-1582)
 ├─ OUT_OF_MEMORY: 使用 num_oom_retries_left（-1 表示无限）
 ├─ NODE_DIED 且原因为 AUTOSCALER_DRAIN_PREEMPTED 且 task 可重试: 不扣次数
 ├─ 其他: num_retries_left--（-1 表示无限）
 ├─ enable_output_error_log_if_still_retry: 向 driver 推送 "还剩 N 次" 日志
 └─ delay = GetTaskRetryDelayMs(attempt, error_type) → async_retry_task_callback_
        → CoreWorker::AsyncRetryTask (core_worker.cc L5154): attempt_number+1，放入 to_resubmit_ 优先队列
        → InternalHeartbeat (L1085-1108) 到期后重新提交给对应的 submitter
```

### 2.3 重试延迟

`task_manager.h` L61-73 的 `GetTaskRetryDelayMs`：

| 错误类型 | 延迟策略 | 配置（`ray_config_def.h`） |
|---|---|---|
| `OUT_OF_MEMORY` | 指数退避，上限 60s | `task_oom_retry_delay_base_ms=1000`（L592） |
| `ACTOR_UNAVAILABLE` | 指数退避 | `task_actor_unavailable_retry_delay_base_ms=100`、`..._max_delay_ms=5000`（L596/599） |
| 其他 | 固定延迟 | `task_retry_delay_ms=0`（L588） |

### 2.4 不会重试或立即失败的情况

`task_manager.cc` 中的相关逻辑：

| 情况 | 结果 | 位置 |
|---|---|---|
| task 已被取消 | 返回 `TASK_CANCELLED` | L1617-1623 |
| 有意退出（`IsIntentionalSystemExit`） | 记为 FINISHED，不算失败 | L1625-1629 |
| 返回值写入 plasma 失败 | 立即失败，不重试；`ObjectStoreFull` 会被映射成 **`OUT_OF_MEMORY`**（见 §15） | L1307-1322、L47-63 |
| OOM killer 判定不可重试（`should_retry=false`） | 立即失败 | — |
| 依赖解析失败 | `DEPENDENCY_RESOLUTION_FAILED` | `normal_task_submitter.cc` L47 |

### 2.5 Streaming generator

- 生成器 task 抛出可重试异常时直接 `raise`，不写返回值（`_raylet.pyx` L1909-1923）。
- 重放结果与原先不一致时，抛出 `StreamingGeneratorReplayInconsistentError`（`exceptions.py` L1125）。

## 3. 对象容错

### 3.1 Ownership 与恢复资格

`core_worker/reference_counter_interface.h` L36-49 定义了 `LineageReconstructionEligibility`：

| 资格 | 产生条件 | 对应错误（`OBJECT_UNRECONSTRUCTABLE_*`） |
|---|---|---|
| ELIGIBLE | 由 `max_retries != 0` 的 task 返回 | — |
| INELIGIBLE_PUT | `ray.put` 创建的对象（`core_worker.cc` L1264/1341/2618） | PUT |
| INELIGIBLE_NO_RETRIES | task 的 `max_retries=0` | RETRIES_DISABLED |
| INELIGIBLE_LINEAGE_EVICTED | lineage 超过 `max_lineage_bytes` 后被驱逐 | LINEAGE_EVICTED |
| INELIGIBLE_LINEAGE_DISABLED | `lineage_pinning_enabled=false`，或 job 级 `disable_job_level_lineage_reconstruction` | LINEAGE_DISABLED |
| INELIGIBLE_REF_NOT_FOUND | 引用已经不存在 | REF_NOT_FOUND |

此外：
- 只有 owner 能触发重建，borrower 发现对象丢失时返回 `BORROWED`。
- 重建次数用尽时返回 `MAX_ATTEMPTS_EXCEEDED`；task 已取消时返回 `TASK_CANCELLED`。

> 被提升到 plasma 的内联小返回值不记录所在节点，因此**不可重建**，与本地节点共命运（`task_manager.cc` L693-701 注释）。
> `ray.put(_owner=...)` 已在 Ray 2.56 **移除**，使用会抛 ValueError（`worker.py` L3060-3064）。

### 3.2 恢复流程

```
节点死亡 → owner 订阅到 → ReferenceCounter::ResetObjectsOnRemovedNode (reference_counter.cc L912-927)
         → objects_to_recover_ → 每 100ms 执行 FlushObjectsToRecover (core_worker.cc L604-628)
ray.get 拉取失败 / raylet 上报对象丢失 ↘
ObjectRecoveryManager::RecoverObject (object_recovery_manager.cc L24-91)
 ├─ actor 创建任务的返回值: 跳过（由 GCS 负责）
 ├─ 当前 worker 不是 owner: 失败，原因 BORROWED
 └─ 未 pin 且未 spill: PinOrReconstructObject (L93-107)
       ├─ 有其他副本: PinExistingObjectCopy → 向 raylet 发 PinObjectIDs，把副本升为主副本 (L109-139)
       └─ 没有副本: ReconstructObject (L141-190)
            ├─ 资格不是 ELIGIBLE: recovery_failure_callback_ 写入错误对象
            └─ TaskManager::ResubmitTask(task_id) (task_manager.cc L474-535)
                  └─ num_retries_left 减 1，重新提交；之后对每个依赖递归调用 RecoverObject
失败时: 把 RayObject(error) 放入 store，用户 ray.get 时抛出 ObjectReconstructionFailedError(reason)
```

- **Lineage 占用控制**（`task_manager.cc` L1402-1457）：所有 task spec 的总大小超过 `max_lineage_bytes`（默认 1GiB）时，从最旧的开始驱逐，直到总量降到上限的一半。
- **lineage 释放**：可重建的返回值全部出作用域后，task spec 会被删除（`RemoveLineageReference`，L1771-1822）。
- **关闭重建**：
  - 全局关闭：`RAY_lineage_pinning_enabled=0`（`ray_config_def.h` L208）。
  - 按 job 关闭：`JobConfig` 中的 `disable_job_level_lineage_reconstruction`（`common.proto` L476），优先级高于全局开关（`context.cc` L217-222）。

### 3.3 OwnerDiedError 的产生路径

1. Borrower 调用 `GetObjectStatus` 时 RPC 失败，得到 `OWNER_DIED`；owner 回复 OUT_OF_SCOPE 时得到 `OBJECT_DELETED`，对应 Python 的 `ReferenceCountingAssertionError`（`future_resolver.cc` L52-66）。
2. raylet 订阅 owner 的对象位置失败，同样得到 `OWNER_DIED`（`ownership_object_directory.cc` L354-365）。
3. Borrower 协议细节：`AddBorrowerAddress` 之后调用 `WaitForRefRemoved`，订阅 `WORKER_REF_REMOVED_CHANNEL`。borrower 死亡时同样会触发清理（`reference_counter.cc` L1246-1325）。

> 缓解方法：长生命周期的对象由 detached actor 产生（让它成为 owner），或者由 driver 持有。

### 3.4 Object Spilling（防止对象存储被打满）

```
plasma 分配失败 ──▶ CreateRequestQueue::ProcessRequests (plasma/create_request_queue.cc L85-151)
  ├─ 磁盘使用率 ≥ local_fs_capacity_threshold(0.95) → OutOfDisk
  ├─ 触发全局 GC 和 spill；有 spill 正在进行 → TransientObjectStoreFull（重置宽限期）
  ├─ 在 oom_grace_period_s(2s) 宽限期内 → ObjectStoreFull("Waiting for grace period")
  └─ 宽限期过后 → FallbackAllocate（把对象 mmap 到 fallback 目录，默认 /tmp）
        └─ 仍然失败 → OutOfDisk
定时检查: allocated ≥ object_spilling_threshold(0.8) → SpillObjectUptoMaxThroughput
         (node_manager.cc L2466-2480；只有 object_spilling_config 非空时才注册)
LocalObjectManager::TryToSpillObjects (local_object_manager.cc L162-251)
  按 max_fused_object_count(2000)、max_spilling_file_size_bytes 把小对象合并后写出，由 IO worker 执行
```

**配置方式**（目录优先级见 `node.py` L2275-2323）：

```python
ray.init(object_spilling_directory="/mnt/nvme/spill")       # 推荐
# 或使用旧接口（会打印 unstable API 警告）:
ray.init(_system_config={"object_spilling_config": json.dumps(
    {"type": "filesystem", "params": {"directory_path": "/mnt/nvme/spill"}})})
# 也可以 spill 到 S3（smart_open，需要 boto3）:
# {"type": "smart_open", "params": {"uri": "s3://bucket/path"}}
```

- **默认 spill 目录**：`{session_dir}/ray_spilled_objects_<node_id>`。
- **后端实现**：`_private/external_storage.py`，`FileSystemStorage` 在 L278，`ExternalStorageSmartOpenImpl` 在 L410。
- **IO worker 并发数**：`max_io_workers=4`。单次最小 spill 量为 `min_spilling_size=100MiB`。
- **磁盘监控**：由 `FileSystemMonitor`（`common/file_system_monitor.cc`）负责，检查周期 `local_fs_monitor_interval_ms=100`。

## 4. Actor 容错

### 4.1 选项

定义在 `_common/ray_option_utils.py` L143、L246-258：

| 选项 | 默认值 | 语义 |
|---|---|---|
| `max_restarts` | 0 | actor 进程意外死亡后的重启次数，`-1` 表示无限 |
| `max_task_retries` | 0 | actor 方法因系统故障失败时的重试次数，`-1` 表示无限；也可以在单个方法上用 `@ray.method(max_task_retries=..)` 或 `.options()` 覆盖（`actor.py` L712、L1098） |
| `retry_exceptions` | False | 对应用异常是否重试，与 `max_task_retries` 配合使用 |
| `max_pending_calls` | -1 | 待处理调用数的上限，超出时抛 `PendingCallsLimitExceeded`（`actor_task_submitter.cc` L921-926） |
| `lifetime` | None（non_detached） | 设为 `"detached"` 时 actor 与 owner 解耦 |
| `name` / `namespace` / `get_if_exists` | — | 具名 actor；`get_if_exists=True` 必须同时指定 name（L411） |

```python
@ray.remote(max_restarts=-1, max_task_retries=-1)
class Worker:
    def __init__(self):
        self.state = load_checkpoint_or_default()   # 重启时会重新执行 __init__
    def step(self, x):
        ...; save_checkpoint(self.state)
```

完整示例见 `doc/source/core/doc_code/actor_checkpointing.py`。

### 4.2 Actor 状态机

```
                 ┌──────────────────────┐
  register ──▶ DEPENDENCIES_UNREADY ──▶ PENDING_CREATION ──▶ ALIVE
                  │ owner 死亡                ▲      │ worker/节点死亡且可重启
                  ▼                          │      ▼
                 DEAD ◀───────── 无剩余次数 ── RESTARTING
                  ▲                                 │ 重新调度
                  └───── ray.kill / exit_actor / out-of-scope / owner 死亡
```

详见 `src/ray/design_docs/actor_states.md` L3-59。这份文档**遗漏了抢占例外**，见 §15。

### 4.3 GCS 侧重启逻辑

代码在 `gcs/actor/gcs_actor_manager.cc`。

**`OnWorkerDead`（L1213-1306）**
- 退出类型为 `INTENDED_USER_EXIT` 或 `USER_ERROR` 时**不重启**。
- 销毁以该 worker 为 owner 的子 actor。
- 销毁依赖尚未就绪的 actor。
- 对该 worker 上承载的 actor 调用 `RestartActor`。

**`OnNodeDead`（L1308-1434）**
- 销毁 owner 位于该节点上的子 actor。
- 对正在该节点调度或已在该节点创建的 actor，调用 `CancelOnNode` 后执行 `RestartActor`。

**`RestartActor`（L1465-1645）**，核心计算如下：

```cpp
// gcs_actor_manager.cc L1504-1525
else if (max_restarts == -1) { remaining_restarts = -1; }
else {
  // Restarts due to node preemption do not count towards max_restarts.
  const auto effective_restarts = num_restarts - num_restarts_due_to_node_preemption;
  remaining_restarts = std::max(max_restarts - effective_restarts, 0);
}
if (remaining_restarts != 0 ||
    (need_reschedule && max_restarts > 0 && mutable_actor_table_data->preempted())) {
  // → RESTARTING: num_restarts++, 清空地址, 持久化, Publish, Schedule
} else {
  // → DEAD: 写入 death_cause; detached actor 额外调用 DestroyActor
}
```

- 每次进入 `RestartActor`，都会销毁该 actor **自己拥有的 PG**（L1503）。
- `OnActorCreationSuccess` 会把 `preempted` 标记重置为 false（L1742）。
- **lineage 重建触发的 actor 重启**：`HandleRestartActorForLineageReconstruction`（L361-440），用 `num_restarts_due_to_lineage_reconstruction` 保证幂等。
- **死亡原因**：`ActorDeathCause`（`common.proto` L366-402）。`ActorDiedErrorContext.Reason` 的取值为 WORKER_DIED、OWNER_DIED、NODE_DIED、RAY_KILL、OUT_OF_SCOPE、REF_DELETED。

### 4.4 调用侧行为（ActorTaskSubmitter）

```
GCS actor 状态 pubsub → ActorManager::HandleActorStateNotification (actor_manager.cc L231-268)
  RESTARTING → DisconnectActor(dead=false): 正在执行的任务注入 IOError("The actor was restarted")，由 TaskManager 决定是否重试
  DEAD       → DisconnectActor(dead=true):  所有排队任务以 death_cause 失败（不重试）
  ALIVE      → ConnectActor: 发送排队中的任务
```

| 场景 | `max_task_retries == 0` | `max_task_retries != 0` |
|---|---|---|
| actor 处于 RESTARTING 时提交任务 | **立即失败**（`fail_if_actor_unreachable`，`actor_task_submitter.cc` L551-569） | 排队等待 ALIVE，**不消耗**重试次数 |
| 执行中的任务所在 actor 崩溃 | 失败，抛 `ActorDiedError` 或 `ActorUnavailableError` | 消耗一次重试并重新发送 |
| PushTask 网络失败，但 actor 尚未确认死亡 | `ActorUnavailableError` | 按 `ACTOR_UNAVAILABLE` 做指数退避后重试（L709-746） |
| 重试用尽后 actor 状态未知 | 等待 `timeout_ms_task_wait_for_death_info`（1000ms）取得死因；如果节点被抢占，报 `ACTOR_DIED`（AUTOSCALER_DRAIN_PREEMPTED）（L769-787、L485-533） | 同左 |
| 向已经 DEAD 的 actor 提交任务 | 立即以 death_cause 失败（L245-270） | 同左 |

- **重试顺序**：重试任务总是**乱序**执行，会插队优先发送（`sequential_actor_submit_queue.cc` L155-170；`actor.py` L1810）。
- **非幂等方法**：开启 `max_task_retries` 前要确认方法是否能安全地重复执行。

### 4.5 Owner、detached 与终止方式

**Owner 与 detached**
- **non-detached actor 与 owner 共命运**：
  - GCS 在注册时对 owner 发起 `PollOwnerForActorRefDeleted` 长轮询（L757、L955-999）。owner 死亡或引用全部释放时，GCS 调用 `DestroyActor`。
  - raylet 侧也有兜底：kill 那些 owner 已死的 leased worker，detached actor 除外（`node_manager.cc` L1032-1052）。
- **detached actor**：不随 owner 和 job 结束而销毁，只能用 `ray.kill` 结束。GCS 重启后会重新加载（`OnInitializeActorShouldLoad`，L150-196）。

**终止方式对比**

| 方式 | 实现 | 是否重启 | 是否先执行排队任务 |
|---|---|---|---|
| `ray.kill(a)`（`no_restart=True`，默认） | GCS `DestroyActor(RAY_KILL)` | 否 | 否，强制 kill |
| `ray.kill(a, no_restart=False)` | GCS `KillActor`，worker 以 INTENDED_SYSTEM_EXIT 退出后进入 RestartActor | **是，消耗一次重启次数** | 否 |
| `a.__ray_terminate__.remote()` | 调用 `exit_actor()` | 否 | 是，并执行 atexit |
| actor 内部调用 `ray.actor.exit_actor()` | 以 INTENDED_USER_EXIT 退出 | 否 | — |
| 句柄全部出作用域 | `DestroyActor(OUT_OF_SCOPE)`，graceful，超时 `actor_graceful_shutdown_timeout_ms=30000` 后改为强制 kill | 否 | — |

|---|---|---|

```
GCS HandleDrainNode (gcs_autoscaler_state_manager.cc L486-552)
 ├─ SetPreemptedAndPublish(node): 把节点上所有 actor 标记为 preempted=true（在 DrainRaylet 之前执行，且不区分原因，见 §15）
```

## 7. Placement Group 容错

代码在 `gcs/gcs_placement_group_manager.cc`。

1. **`OnNodeDead`**（L695-765）：
   - 调用 `GetAndRemoveBundlesOnNode`，把丢失 bundle 的 node_id 清空。
   - CREATED 状态的 PG 改为 **RESCHEDULING**，以 rank 0（最高优先级）放回 pending 队列，持久化后重新调度。
   - 对拓扑约束类 PG：所有 bundle 都丢失时，从 infeasible 队列移回 pending 队列。
2. **调度失败时**：RESCHEDULING 状态的 PG 调度失败后会以 rank 0 重新入队，但不立即重试，以避免重试风暴（L227-242）。
3. **PG 内的 actor**：由 `GcsActorManager::OnNodeDead` 独立处理，按 `max_restarts` 规则重启，并重新调度到重建后的 bundle 上。
4. **限制**：
   - PG 被删除时，其中的 task/actor 抛出 `TaskPlacementGroupRemoved` 或 `ActorPlacementGroupRemoved`。
   - 同时满足"可重启 + detached + 使用 PG"时，Ray 会给出告警（`actor.py` L2079-2085）。
   - actor 重启时会销毁它自己创建的 PG。
5. **作业结束**：job 结束时会调用 `CleanPlacementGroupIfNeededWhenJobDead`（`gcs_server.cc` L1307-1312）。

## 9. 资源保护：OOM、磁盘、对象存储、cgroup、Worker 数

### 9.1 OOM 防护（raylet 内存监控与 Worker Killer）

```
MemoryMonitor (common/monitors/multi_memory_monitor_factory.cc L29-76，仅 Linux)
 ├─ ThresholdMemoryMonitor: 每 memory_monitor_refresh_ms(250) 读取 /proc 和 cgroup
 │     阈值 = max(total*memory_usage_threshold(0.95), total - min_memory_free_bytes)
 │     开启资源隔离时，阈值改为 user cgroup 的 memory.high
 ├─ EventMemoryMonitor（开启资源隔离时使用）: inotify 监听 memory.events 中 high 计数的增长
 └─ PressureMemoryMonitor（PSI）: 已实现但未接入（§15）
 触发后先 Disable 去抖 → NodeManager kill 回调 (node_manager.cc L3156-3287)
   SelectWorkersToKill → SetWorkerFailureReason(OUT_OF_MEMORY, should_retry)
   → DestroyWorker(NODE_OUT_OF_MEMORY, force) → 上报 "Out of Memory" 事件
   → owner 通过 GetWorkerFailureCause 拿到 OOM 原因，按 task_oom_retries 决定是否重试
```

**Worker Killing 策略**（`raylet/worker_killing_policy_factory.cc`）：

| 策略 | 开关 | 选择规则 | 一次 kill 的数量 |
|---|---|---|---|
| **TimeBased**（默认） | — | 排序优先级依次为：idle 优先于有 lease，可重试优先于不可重试，普通 task 优先于 actor，lease 授予越晚越优先，idle 之间内存越大越优先（`worker_killing_policy_by_time.cc` L114-167） | **可以多个**，直到释放量 ≥ `used - threshold + kill_buffer` |
| GroupByOwner（旧策略） | `RAY_worker_killing_policy_by_group=1` | 按 owner 分组：可重试组优先，组越大越优先，组内后进先出（LIFO） | 1 个；组内最后一个成员标记为不重试 |

- `kill_buffer = min(total*5%, max_kill_memory_buffer_bytes=3GiB)`。
- 冷启动的 idle worker，内存超过 `idle_worker_killing_memory_threshold_bytes=1GB` 才会成为候选。
- **OOM 重试**：`task_oom_retries=-1`（无限），以 `task_oom_retry_delay_base_ms=1000` 为基数指数退避，上限 60s。
- **关闭 OOM killer**：`RAY_memory_monitor_refresh_ms=0`。
- **报错内容**：`OutOfMemoryError` 的文案由 raylet 生成，包含节点内存用量和各进程的内存占用，并给出调参建议（`node_manager.cc` L3389-3474）。
- 文档：`doc/source/core/scheduling/ray-oom-prevention.md`。

### 9.2 cgroup v2 资源隔离（保护系统进程）

```bash
ray start --head --enable-resource-isolation \
  --system-reserved-cpu=2 --system-reserved-memory=8GB [--cgroup-path=/sys/fs/cgroup]
```

**参数默认值**（`scripts.py` L749-787；`ray_constants.py` L65-94）：
- 预留 CPU：`min(3, max(1, 5% 核数))`。
- 预留内存：`min(10GB, max(500MB, 10% 内存))`。

**cgroup 层级**（`cgroup_manager_interface.h` L120-125）：

```
ray-node_<id>/
├── system/leaf          ← raylet、gcs、dashboard 等，memory.low = 预留内存
└── user/
    ├── workers          ← Ray worker，memory.high = min(total - 预留, total*user_memory_proportion_high)
    └── non-ray          ← memory.max = total*user_memory_proportion_max
```

- 约束值的计算在 `linux_cgroup_manager_factory.cc` L59-78。CPU 的 `cpu.weight` 取 `预留/总量*10000`。
- **效果**：用户代码内存失控时，先撞上 user cgroup 的 `memory.high`，触发 EventMemoryMonitor 去 kill worker，避免 raylet 和 GCS 被内核 OOM killer 误杀。
- 文档：`doc/source/core/resource-isolation-with-cgroupv2.md`。其中关于"保证 system = reserved + object store"的描述与代码不符，见 §15。


**Reconciler**（`reconciler.py`）：
- 被动同步云厂商和 Ray 的实际状态（L176-240），例如 Ray 节点 DEAD 时映射为 RAY_STOPPED。

- 处理卡住的实例（`_handle_stuck_instances`，L1066-1185）。超时默认值来自 `InstanceReconcileConfig`（`config.py` L84-125）：

## 11. Job 级容错

### 11.1 Ray Jobs（`dashboard/modules/job/`）

```
JobManager.submit_job → 创建 JobSupervisor actor（detached、具名，未设置 max_restarts，因此不会重启）(job_manager.py L587-602)
JobSupervisor → 启动 entrypoint 子进程（另有 watcher 子进程：supervisor 一死就 kill -9 整个进程组）(job_supervisor.py L216-232)
JobManager 监控循环（每 1s 调用 ping.options(max_task_retries=-1)）(L158-359)
   PENDING 超过 RAY_JOB_START_TIMEOUT_SECONDS(900s) → FAILED
   RuntimeEnvSetupError / ActorUnschedulableError / ActorDiedError → 对应错误码，状态 FAILED
entrypoint 退出码 0 → SUCCEEDED；非 0 → FAILED(JOB_ENTRYPOINT_COMMAND_ERROR)，附日志尾部
stop_job → SIGTERM（RAY_JOB_STOP_SIGNAL），等待 RAY_JOB_STOP_WAIT_TIME_S(3s) 后 SIGKILL → STOPPED
```

- **不支持 entrypoint 自动重试**，失败即进入终态。需要重试时，可以由外部系统（如 KubeRay RayJob 的 `backoffLimit`）重新提交。
- **dashboard 或 head 重启后恢复**：job 信息存储在 GCS KV 中，`_recover_running_jobs`（L111-126）会重新挂上监控。JobManager 的 docstring 说"不持久化"，与实际不符，见 §15。

### 11.2 Driver 退出时的清理

- raylet 的 `HandleJobFinished`（`node_manager.cc` L608-637）强制结束属于该 job、且不属于 detached actor 的 worker。
- non-detached actor 以 `OWNER_DIED` 原因销毁，PG 被清理。
- `GcsTaskManager::OnJobFinished` 在延迟 15s 后，只把**观测数据**中未结束的 task 标记为 FAILED（`gcs_task_manager.cc` L752-773），不负责实际的进程清理。
- driver 所在节点死亡时，`GcsJobManager::OnNodeDead` 把相关 job 标记为结束（`gcs_job_manager.cc` L479-503）。

## 16. 最佳实践

1. **Task 要幂等**。默认会重试 3 次，有副作用的 task 要么做好幂等，要么设置 `max_retries=0`。注意 `max_retries=0` 同时会关闭 OOM 重试和 lineage 重建。
2. **对应用异常的重试要谨慎**。只对瞬时错误开启，例如 `retry_exceptions=[ConnectionError]`，避免对确定性的 bug 反复重试。
3. **需要容错的 actor**：设置 `max_restarts=-1` 加 `max_task_retries=-1`，在 `__init__` 中从外部存储恢复状态，方法本身保持幂等。
4. **长生命周期的服务**：使用 `lifetime="detached"` 加具名 actor，并配合 GCS FT；否则 driver 一退出，actor 就随之销毁。
5. **对象的 owner 要放在稳定的进程上**。关键大对象由 driver 或 detached actor 产生。尽量少用 `ray.put` 生成需要容错的对象，因为这类对象不可重建。
6. **生产环境开启 GCS FT**：在 KubeRay 中配置 Redis 和 `RAY_external_storage_namespace`，并把 worker 的 `RAY_gcs_rpc_server_reconnect_timeout_s` 调大到 600。
7. **内存保护**：开启 `--enable-resource-isolation`，并配置好 spill 目录（使用独立的 NVMe 盘）。需要为 task 预留内存时，使用 `memory=` 资源做调度，而不是依赖 OOM killer 兜底。
8. **使用 Spot 实例**：依靠 drain 和抢占机制（重试不计次）。让节点在收到 SIGTERM 时触发 `RAY_GRACEFUL_SHUTDOWN_DRAIN_TIMEOUT_S`，Train 中再配置 `max_preemption_failures`。
9. **AI 库的容错**：
   - Serve：实现 `check_health`，调好 graceful shutdown 时长。
   - Train：设置 `FailureConfig(max_failures)`，定期 `report(checkpoint=...)`。
   - Tune：配置 `Tuner.restore`。
   - Data：设置 `max_errored_blocks`，允许少量坏数据。
10. **混沌演练**：在测试环境中用 `RAY_testing_rpc_failure` 和 `ray_start_chaos_cluster` 验证业务的容错逻辑。
