### 1.2 用户自定义指标 API（`python/ray/util/metrics.py`）

| 类 | 行号 | 方法 | 约束 |
|---|---|---|---|
| `Metric` 基类 | L41-171 | `set_default_tags(dict)`（可链式调用）、`info` | `tag_keys` 必须是 `tuple[str]`，否则抛 TypeError（L67-74） |
| `Counter` | L174-238 | `inc(value=1.0, tags=None)` | `value > 0`（L235） |
| `Gauge` | L319-370 | `set(value, tags=None)` | `set(None)` 是空操作（L359） |
| `Histogram` | L241-316 | `observe(value, tags=None)` | `boundaries` 不能为空，且每个值都 > 0（L266-277） |

**规则：**

- **名字校验**：
  - 正则是 `^[a-zA-Z_:][a-zA-Z0-9_:]*$`（L23）。
  - 名字为空时抛 ValueError。
  - 名字不合法时**只发 UserWarning**，并把该指标标记为丢弃，之后的 record 都是空操作（L26-38、L126-127）。
  - 名字含 `:` 时会发 FutureWarning（L76-82）。
- **标签合并**：`{**default_tags, **tags}`，调用时传入的 tags 优先（L143）。缺少任何一个 `tag_keys` 都会抛 ValueError（L145-154）。
- **Counter 的后端**：OTel 模式下是 `CythonCount`，旧模式下是 `CythonSum`（L203-217）。docstring 说明：从 2.10 起 counter 同时导出 `_total` 和一个同名 gauge，可用 `RAY_EXPORT_COUNTER_AS_GAUGE=0` 关闭 gauge。
- **可序列化**：三个类都实现了 `__reduce__`，可以直接作为参数传给 task 或 actor。
- **调用链**：
  1. `metrics.py`
  2. `includes/metric.pxi` L27-47：`with nogil: self.metric.get().RecordForCython(...)`
  3. `src/ray/stats/metric.cc` L175 `RecordForCython`
  4. `Record`
  5. `OpenTelemetryMetricRecorder::SetMetricValue`

**最小示例**（取自 `doc/source/ray-observability/doc_code/metrics_example.py`）：

```python
import ray, time
from ray.util.metrics import Counter, Gauge, Histogram

ray.init(_metrics_export_port=8080)   # 固定端口，方便直接 curl

@ray.remote
class MyActor:
    def __init__(self, name):
        self.counter = Counter("num_requests", description="...", tag_keys=("actor_name",))
        self.counter.set_default_tags({"actor_name": name})
        self.gauge = Gauge("curr_count", description="...", tag_keys=("actor_name",))
        self.hist = Histogram("request_latency", description="ms",
                              boundaries=[0.1, 1], tag_keys=("actor_name",))
    def process(self, n):
        t = time.time()
        self.counter.inc()
        self.gauge.set(n, tags={"actor_name": "x"})
        self.hist.observe(1000 * (time.time() - t))

# curl localhost:8080/metrics | grep ray_num_requests
```

> 导出时指标名会加上 `ray_` 前缀，例如 `num_requests` 导出为 `ray_num_requests_total`（counter 带 `_total`）。

### 1.3 C++ 指标框架（`src/ray/stats/`、`src/ray/observability/`）

- **类型**：`Gauge`（`metric.h` L159）、`Histogram`（L177）、`Count`（L199）、`Sum`（L217），都继承 `Metric : observability::MetricInterface`（L104）。
- **OTel 映射**（`metric.cc` L185-245）：

  | Ray 类型 | OTel instrument |
  |---|---|
  | Gauge | ObservableGauge |
  | Count | Counter |
  | Sum | UpDownCounter |

### 1.6 基数控制（Cardinality）

- 定义在 `python/ray/_private/telemetry/metric_cardinality.py` L27-109，共三档：
  - `legacy`：保留全部标签。
  - `recommended`：对 `tasks`、`actors`、`task_retry_submissions`、`object_recovery_attempts` 去掉 `WorkerId`。
  - `low`：在 recommended 的基础上，对 `tasks`、`actors`、`task_retry_submissions` 再去掉 `Name`。
- **默认值两侧不一致**：C++ 的 `metric_cardinality_level` 默认是 `"legacy"`（`ray_config_def.h` L729），Python 的 `RAY_METRIC_CARDINALITY_LEVEL` 默认是 `"recommended"`（`ray_constants.py` L768-770）。
- 生效位置：OTel 路径在 agent 端聚合前丢弃标签（`open_telemetry_metric_recorder.py` L160-191），所以 **Python 侧的设置才是最终决定**。
- 大规模集群出现标签爆炸时，设置 `RAY_metric_cardinality_level=low`。

## 6. 分布式追踪 Tracing

**实现**：`python/ray/util/tracing/tracing_helper.py`，基于 OpenTelemetry。

```
driver: f.remote()
  @_tracing_task_invocation (remote_function.py L360)
   └─ span "<fn> ray.remote" (PRODUCER)
      kwargs["_ray_trace_ctx"] = _DictPropagator.inject_current_context()   (L311-342)
          │ 随 task 参数传递
worker: _inject_tracing_into_function (L345-383)
   └─ extract(_ray_trace_ctx) → span "<fn> ray.remote_worker" (CONSUMER)
Actor: _tracing_actor_creation (L386) / _tracing_actor_method_invocation (L429)
       _inject_tracing_into_class (L469)，generator 方法和 __del__ 不包装
```

**启用流程：**

1. 通过 `ray.init(_tracing_startup_hook="my_mod:setup_tracing")`（`worker.py` L1656、L1906）或 `ray start --head --tracing-startup-hook=my_mod:setup_tracing`（`scripts.py` L701-707，hidden 参数）指定 hook。
2. Node 把 hook 写入 GCS KV，命名空间是 `tracing`（`node.py` L1683-1691）。
3. **每个 worker 在 connect 时**读取 KV，调用 `_enable_tracing()`，再执行 hook（`worker.py` L2780-2789）。

**Hook 示例**（`util/tracing/setup_local_tmp_tracing.py`）：

```python
# my_mod.py —— 每个节点都必须能 import 到（可以放进 runtime_env 的 py_modules）
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

def setup_tracing() -> None:
    trace.set_tracer_provider(TracerProvider())
    trace.get_tracer_provider().add_span_processor(
        BatchSpanProcessor(OTLPSpanExporter(endpoint="http://jaeger:4317", insecure=True)))
```

**自定义 span**：在 task 内部直接使用 `trace.get_tracer(__name__).start_as_current_span("x")`，它会自动挂在 Ray 注入的父 span 下。

- **依赖**：`pip install opentelemetry-api opentelemetry-sdk`，按需安装 exporter。
- **参考文档**：`doc/source/ray-observability/user-guides/ray-tracing.md`；另有 `setup_tempo_tracing.py` 示例。
- **注意**：开启后函数签名里会多一个 keyword-only 参数 `_ray_trace_ctx`。

## 10. 自定义开发指南

### 10.1 添加应用指标（Python）

参见 §1.2。建议：

- 标签值必须是 str，不要用 task_id、request_id 这类高基数值作标签。
- 在 actor 的 `__init__` 中创建指标对象并复用，避免每次调用都重新构造。
- 生产环境用 `--metrics-export-port` 固定端口，或使用 SD 文件做服务发现。
- Serve 应用优先使用 `ray.serve.metrics`，它会自动附带 deployment、replica 标签。
- 测试可以参考 `python/ray/tests/test_metrics_agent.py` 的写法：抓取 `/metrics` 后断言。

### 10.2 新增 C++ 内置指标

1. 在对应组件的 `metrics.h`（如 `src/ray/raylet/metrics.h`）中仿照 §1.3 添加一个 inline 工厂函数，返回 `ray::stats::{Gauge,Count,Sum,Histogram}`。
   - Histogram 需要传 boundaries。
   - 名字要满足 `^[a-zA-Z_:][a-zA-Z0-9_:]*$`，否则会 `RAY_CHECK` 崩溃。
2. 在组件里持有这个对象，例如作为成员或通过构造注入（参考 `core_worker_process.cc` 的做法），调用 `metric.Record(value, {{"Tag", "v"}})`。
3. 如果新指标带高基数标签，需要同步更新 `python/ray/_private/telemetry/metric_cardinality.py` 的规则。
4. 需要在 Grafana 中展示时，到 `dashboard/modules/metrics/dashboards/*_panels.py` 添加 Panel。
5. 更新文档 `doc/source/ray-observability/reference/system-metrics.md`。
6. 测试：C++ 侧参考 `src/ray/stats/tests/metric_with_open_telemetry_test.cc`，Python 侧参考 `python/ray/tests/test_metrics_agent.py`。

### 10.3 新增 Dashboard 模块

模块会被自动发现（`dashboard/utils.py` L305-341 用 `pkgutil.walk_packages` 加 `__subclasses__()`），**不需要注册**。

**推荐方式：SubprocessModule**（独立进程，崩溃后自动重启）

```python
# python/ray/dashboard/modules/my_mod/my_head.py
from aiohttp.web import Request, Response
import ray.dashboard.optional_utils as optional_utils
import ray.dashboard.utils as dashboard_utils
from ray.dashboard.subprocesses.module import SubprocessModule
from ray.dashboard.subprocesses.routes import SubprocessRouteTable as routes

class MyHead(SubprocessModule):
    @classmethod
    def is_enabled(cls) -> bool:          # 可选，用来做特性开关
        return True

    @routes.get("/api/my_mod/hello")
    async def hello(self, req: Request) -> Response:
        # self.gcs_client / self.http_session 都是懒初始化的
        return optional_utils.rest_response(
            status_code=dashboard_utils.HTTPStatusCode.OK, message="ok", data={"x": 1})
```

**主进程模块：DashboardHeadModule**（参考 `modules/tests/test_head.py`）

```python
import ray.dashboard.optional_utils as dashboard_optional_utils
import ray.dashboard.utils as dashboard_utils
routes = dashboard_optional_utils.DashboardHeadRouteTable

@dashboard_utils.dashboard_module(enable=True)
class MyInProcHead(dashboard_utils.DashboardHeadModule):
    @staticmethod
    def is_minimal_module(): return False
    async def run(self): ...                 # 必须实现，可以写后台循环
    @routes.get("/api/my_inproc")
    async def get(self, req): ...
```

**Agent 模块**：继承 `DashboardAgentModule`（`utils.py` L63-93），实现 `async run(self, server)`。可以在 `server` 上注册 gRPC servicer；HTTP 路由用 `DashboardAgentRouteTable`（参考 `reporter/healthz_agent.py`）。

**约束：**

- 类名必须全局唯一（`head.py` L333-338）。
- 路由路径不能重复，重复时注册直接抛异常（`routes.py` L121-127）。
- `SubprocessModule` 不能作为 minimal 模块。
- 返回值统一使用 `rest_response`，格式为 `{"result","msg","data"}`。
- 只想加载部分模块做调试时，用 `dashboard.py --modules-to-load=MyHead`。

### 10.8 新增可观测相关的 RAY_CONFIG

在 `src/ray/common/ray_config_def.h` 中加上 `/// 注释` 和 `RAY_CONFIG(type, name, default)`。之后就能通过 `RAY_<name>` 环境变量或 `_system_config` 覆盖。如果 Python 侧也要读取，在 `_private/ray_constants.py` 中用 `env_bool`/`env_integer` 读取同名变量，**注意两边的默认值要保持一致**（参见 §1.6 的反例）。

## 12. 常见坑点

1. **注释与默认值不一致**：`enable_open_telemetry` 的注释说默认使用 OpenCensus，实际默认是 OTel。`metric_cardinality_level` 的 C++ 默认值和 Python 默认值不同。Usage Stats 文件头注释前后矛盾。以上都以代码为准。
2. **非法指标名在 Python 侧不报错**：只发 UserWarning，指标被静默丢弃，看不到数据时先检查 warnings。C++ 侧则会直接崩溃。
3. **Counter 会多出一个同名 gauge**：导出 `_total` counter 的同时还会导出同名 gauge（兼容旧行为），写 PromQL 时注意区分。
4. **metrics 端口默认随机**：Prometheus 要么用 SD 文件（`/tmp/ray/prom_metrics_service_discovery.json`），要么固定 `--metrics-export-port`。内置的 `prometheus.yml` 写死了 `/tmp/ray/...` 路径，修改 `--temp-dir` 后需要同步调整。
5. **Grafana 嵌入问题**：浏览器能访问的地址和 head 能访问的地址不同时，必须设置 `RAY_GRAFANA_IFRAME_HOST`。Grafana 还要开启 `allow_embedding`，Ray 生成的 `grafana.ini` 已经包含这一项。
6. **C++ 日志默认不轮转**：raylet.out、gcs_server.out 在长期运行的集群中可能无限增长，生产环境应设置 `RAY_ROTATION_MAX_BYTES`。
7. **`task_events_report_interval_ms=0` 会让 State API 和 Dashboard 看不到 task**。timeline 文档却要求设为 0，两者矛盾，要按需取舍。
8. **task 事件有上限**：GCS 默认只保留 10 万个 task，worker 端也有缓冲上限，大作业会丢弃事件。State API 返回 warnings 时，说明结果不完整。
9. **Export 事件轮转参数可能失效**：`RAY_EXPORT_EVENT_MAX_FILE_SIZE_BYTES` 和 `RAY_EXPORT_EVENT_MAX_BACKUP_COUNT` 在 `ray_constants.py` L721-725 中用 `env_bool` 读取，疑似 bug，设置数值可能不生效。
10. **Profiling 默认关闭**：需要设置 `RAY_DASHBOARD_ENABLE_PROFILING=1`，而且需要 ptrace 权限，容器中要加 `SYS_PTRACE` 或允许 sudo。内存 profiling 需要安装 `ray[observability]`（memray）。
11. **minimal 安装没有 Dashboard、指标导出和 State API**：`pip install ray` 是 minimal 安装，需要 `ray[default]`。
12. **Tracing hook 的可达性**：hook 必须能在每个 worker 上被 import，否则 worker 启动失败。开启后 remote 函数会多出 `_ray_trace_ctx` 参数。
13. **`log_to_driver` 刷屏**：大规模任务的日志会淹没 driver 并拖慢它，可以设置 `log_to_driver=False`，或用 `RAY_DEDUP_LOGS_SKIP_REGEX` 过滤。
14. **Ray Event 处于 alpha 阶段**：格式和配置方式都可能变化（`ray-event-export.md` L15-17），而且每个节点都要设置环境变量。
